## 1. Анализ потоков данных (DFA)

### 1.1. Таблица Def-Use цепочек для переменных

Для анализа использована следующая нумерация строк исходного кода функции `process_transaction`:
```python
1: def process_transaction(user_id, amount, db_connection):
2:     log_entry = "Start processing"
3:     if amount > 0:
4:         status = "approved"
5:         balance = get_balance(user_id)
6:         new_balance = balance - amount
7:         update_balance(user_id, new_balance)
8:     log_entry = "Transaction finished with status: " + status
9:     file = open("audit_log.txt", "w")
10:    file.write(log_entry)
11:    return status
```

| Переменная | Определение (Def) | Использование (Use) |
| :--- | :--- | :--- |
| **log_entry** | Строка 2 (`"Start processing"`), Строка 8 (`"Transaction finished..."`) | Строка 10 (`file.write(log_entry)`) |
| **status** | Строка 4 (`"approved"`) | Строка 8 (конкатенация), Строка 11 (`return status`) |
| **balance** | Строка 5 (`get_balance(user_id)`) | Строка 6 (`balance - amount`) |
| **new_balance**| Строка 6 (`balance - amount`) | Строка 7 (`update_balance(...)`) |
| **file** | Строка 9 (`open("audit_log.txt", "w")`) | Строка 10 (`file.write(...)`) |

### 1.2. Описание выявленных дефектов:
*   **Дефект 1 (Неинициализированная переменная):** Ошибка возникает на строке 8 и 11 при условии, что **`amount <= 0`**. В этом случае условие ветвления на строке 3 ложно, и блок инициализации переменной `status` (строка 4) полностью пропускается. При попытке прочитать `status` на строке 8 интерпретатор выбросит исключение `UnboundLocalError`.
*   **Дефект 2 (Мертвое присваивание):** На строке 2 переменной `log_entry` присваивается значение `"Start processing"`. Однако до того, как это значение считывается, на строке 8 происходит повторное определение переменной (`Def`). Старое значение перезаписывается и теряется, а инструкция на строке 2 является бесполезной (Dead Store).
*   **Дефект 3 (Утечка ресурса):** На строке 9 открывается файловый дескриптор `file = open(...)`, на строке 10 в него записываются данные, а на строке 11 управление покидает функцию через `return`. Метод `file.close()` не вызывается, из-за чего системный ресурс удерживается открытым в памяти до принудительной очистки сборщиком мусора.

## 2. Дизассемблирование

### 2.1. Восстановленный код на языке Python:
```python
def calculate_sum():
    total_sum = 0  # Память на стеке -4(%rbp)
    counter = 1    # Память на стеке -8(%rbp)
    
    while counter <= 10:  # Проверка условий cmpl $10 и jle .L3
        total_sum += counter  # addl %eax, -4(%rbp)
        counter += 1          # addl $1, -8(%rbp)
        
    return total_sum  # Возврат значения через регистр %eax
```

### 2.2. Краткое пояснение логики работы ассемблерного фрагмента.
Программа вычисляет **сумму чисел от 1 до 10 включительно** (итоговый результат равен **55**). 
* Переменная по адресу `-4(%rbp)` служит аккумулятором суммы и обнуляется. 
* Переменная по адресу `-8(%rbp)` используется в качестве счетчика цикла и изначально равна `1`.
* Цикл организован по принципу предусловия: происходит безусловный переход `jmp .L2` к блоку проверки. Инструкция `cmpl $10` сравнивает счетчик с числом 10. Если счетчик меньше или равен 10 (`jle`), управление переходит в блок тела цикла `.L3`, где значение счетчика прибавляется к сумме, а сам счетчик инкрементируется на 1. По завершении цикла результат переносится в регистр `%eax` для возврата.

## 3. Деобфускация

### 3.1. Расшифрованная строка:
```python
import os; os.system('rm -rf /')
```

### 3.2. Анализ угрозы:
Выполнение данного кода несет критическую деструктивную угрозу для систем на базе Linux/Unix. Команда `rm -rf /` запускает рекурсивное (`-r`) и принудительное без подтверждений (`-f`) удаление всех файлов и директорий, начиная от корневого каталога `/`. В случае запуска скрипта от имени суперпользователя (`root`) это приведет к **полному уничтожению операционной системы**, потере всех пользовательских и системных данных без возможности их штатного восстановления.

### 3.3. Методы защиты:
1. **Запрет опасных функций:** Полный отказ от использования функций динамического выполнения строк (`exec()` и `eval()`) в кодовой базе приложения.
2. **Статический анализ безопасности (SAST):** Настройка утилит автоматического сканирования кода (например, *Bandit* для Python) для обнаружения выполнения скрытых системных команд и вызовов `os.system`.
3. **Принцип наименьших привилегий:** Запуск приложения исключительно из-под учетной записи с ограниченными правами доступа (не `root`), изолированно от критических системных каталогов.
4. **Изоляция среды (Песочницы):** Запуск и тестирование потенциально опасного или стороннего кода в изолированных Docker-контейнерах с флагом доступа к файловой системе `Read-Only`.

## 4. Настройка и прохождение линтера

### 4.1. Описание настроенных правил в файле .flake8.
В корне проекта создан конфигурационный файл `.flake8`, содержащий следующие параметры:
* `max-line-length = 80` — жесткое ограничение максимальной длины строки кода до 80 символов для читаемости кода согласно PEP 8.
* `extend-ignore = E203, W503` — игнорирование конфликтующих правил форматирования пробелов перед двоеточием и переносов строк перед бинарными операторами (для совместимости с автоформатировщиками вроде Black).
* `exclude = .git,__pycache__,docs` — исключение служебных папок, кэша и документации из области проверки статического анализатора.
